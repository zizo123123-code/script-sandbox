بص يا صاحبي، إحنا دلوقتي عندنا شوية ملفات قديمة فيها كذا Provider، وكل Provider معمول بطريقة مختلفة ومش منظمين بنفس الشكل. أنا مش عايزك تبدأ إعادة هيكلة أو نقل الكود دلوقتي. عايزك تعمل الأول مرحلة تجميع وترتيب بس. خش على كل Provider لوحده، واقرأ كل الملفات بتاعته وافهم هو شغال إزاي من أول التسجيل والـLogin لحد الـGenerate والـModels والـUpload وكل حاجة متعلقة بيه. ولو لقيت إن فيه حاجة مهمة ناقصة في الملفات الحالية، حاول تدور عليها في باقي المشروع أو الـAPI/Documentation بتاع الـProvider، ولو اتأكدت إنها موجودة ضيف معلومات عنها في التجميع. يعني ما تفترضش إن الملفات الحالية فيها كل حاجة. أنا عايز كل Provider في فولدر لوحده، وجواه ملفات بسيطة ومنظمة، مثلًا: * account.md → التسجيل، Login، Refresh، Session، الحساب بيخلص إمتى * models.md → كل الـModels الموجودة * capabilities.md → Chat، Vision، Image Generation، Audio، Video، Files... إلخ * generation.md → الـRequests الخاصة بالتوليد وطريقة الـFlow * upload.md → رفع الصور والملفات وطريقة استخدامها * limits.md → Rate Limit، Quota، Cooldown، Reset Time * errors.md → أهم الأخطاء وإزاي نعرف إن الحساب أو الـProvider فيه مشكلة * health.md → إزاي نعرف إن الـProvider شغال أو واقع * notes.md → أي تفاصيل خاصة بالمزود ومش موجودة في الحاجات الأساسية وفي الآخر اعمل ملف MD صغير اسمه مثلًا: provider_summary.md يكون فيه ملخص كل اللي اتجمع، وإيه الموجود فعلًا، وإيه اللي مش موجود في الكود الحالي، وإيه اللي لسه محتاج تأكيد. مهم جدًا: ما تعتبرش إن حاجة مش موجودة في الكود معناها إن الـProvider مش بيدعمها. ممكن تكون الميزة موجودة لكن إحنا لسه ماعملناش لها implementation. استخدم: CONFIRMED AVAILABLE_BUT_NOT_IMPLEMENTED UNKNOWN CONFIRMED_UNSUPPORTED وفي المرحلة دي ممنوع تبدأ Migration أو تغير Architecture. إحنا بنجهز Reference منظم الأول، وبعد ما نخلص كل الـProviders هنستخدم المعلومات دي في إعادة البناء. ولو فيه حاجة أنت شايف إنها مهمة للـProvider ومش موجودة في التقسيمة دي، ضيفها. ومتنساش تدور لكل Provider هل عنده Agent system خاص بيه. لو موجود، اجمعه في agent.md كـModule مستقل وقوي، لكن ما تعتبرهوش جزء أساسي أو إجباري من الـProvider.



اقرأ المشروع الحالي بالكامل بهدف تحليل الـProviders الموجودة وتجميع معلوماتها فقط.

# الهدف

نحن الآن في **مرحلة Discovery / Inventory فقط**.

الهدف هو تكوين Reference منظم وكامل لكل Provider موجود في المشروع، حتى نستخدم هذه المعلومات لاحقًا في بناء Architecture جديدة للـProviders بدون فقد أي functionality موجودة حاليًا أو أي capabilities متاحة عند الـProvider ولم يتم تنفيذها بعد.

**مهم جدًا:**

الملفات الحالية الخاصة بالـProviders هي **Reference Material فقط**.

ليست Architecture نهائية.
وليست Source of Truth.
ولا تفترض أن الـimplementation الحالية تحتوي على كل قدرات الـProvider.

قد يكون عندنا Provider تم تنفيذ Chat له فقط، بينما هو يدعم أيضًا Vision أو Image Generation أو Audio أو Agent أو Files وغيرها.

لذلك يجب أن تبحث عن **القدرات الحقيقية للـProvider** وليس فقط ما تم تنفيذه حاليًا في الكود.

# 5. Agent Module

أثناء تحليل كل Provider، ابحث أيضًا هل لديه **Agent أو Agent-like capability مستقلة**.

اعتبر الـAgent:

**Optional Powerful Module**

وليس جزءًا إجباريًا من كل Provider.

وليس هو الـAgent Runtime الأساسي للمنصة.

إذا كان Provider لديه Agent فعليًا، أنشئ:

```text
agent.md
```

وسجل فيه فقط المعلومات التي نستطيع التأكد منها، مثل:

* هل يوجد Agent فعليًا؟
* ماذا يستطيع أن يفعل؟
* هل يدعم Planning؟
* هل يدعم Tool Calling؟
* هل يستطيع تنفيذ خطوات متعددة؟
* هل لديه Sessions؟
* هل لديه Jobs أو Tasks؟
* هل العملية Sync أم Async؟
* هل يوجد Streaming؟
* هل يمكن معرفة Status؟
* هل يمكن Cancel؟
* كيف نحصل على النتيجة؟
* هل لديه Tools مدمجة؟
* هل يمكن إضافة Tools خارجية؟
* ما الـModels التي يمكن استخدام الـAgent معها؟
* هل له Limits خاصة؟
* أي قيود أو متطلبات خاصة بالـAgent

**لا تعتبر الـAgent موجودًا لمجرد أن الـProvider يدعم Tool Calling أو Multi-step Generation.**

يجب أن يوجد دليل واضح على وجود Agent capability حقيقية.

إذا لم يوجد دليل واضح على وجود Agent، سجل:

```text
UNKNOWN
```

ولا تسجل:

```text
UNSUPPORTED
```

إلا إذا كان هناك دليل واضح على أن الـProvider لا يدعم Agent.

**لا تحاول تصميم أو تنفيذ Agent Runtime الخاص بالمنصة الآن.**

**لا تربط Agent الخاص بالProvider بالـCore.**

الهدف الآن فقط:

**اكتشاف وتوثيق Agent capability الخاصة بالـProvider.**

# 27. Verification Pass

بعد الانتهاء من كل Provider، لا تعتبره مكتملًا مباشرة.

راجع:

1. هل كل العمليات المكتشفة لها توثيق؟
2. هل كل `CONFIRMED` لها Evidence؟
3. هل كل `AVAILABLE_BUT_NOT_IMPLEMENTED` مثبتة من مصدر Provider أو documentation؟
4. هل أي Feature اعتبرناها `UNSUPPORTED` لها دليل واضح؟
5. هل `UNKNOWN` بقيت UNKNOWN بدل التخمين؟
6. هل كل Models لها Evidence؟
7. هل Rate Limits لها Evidence؟
8. هل Generation flows موثقة بشكل صحيح؟
9. هل Upload/File flows موثقة؟
10. هل Agent capability تم التحقق منها فعليًا؟
11. هل خلطنا بين Current Implementation وProvider Capability؟
12. هل هناك Provider functionality موجودة خارج الملفات الرئيسية ولم يتم توثيقها؟
